# 系统架构

本文说明系统如何分层、各模块承担什么职责，以及几个影响全局的技术决策与其取舍。

---

## 一、总体形态

单体应用，前后端分离，构建后由后端同源托管。

```
┌────────────────────────────────────────────────────────────┐
│  浏览器                                                     │
│  Vue 3 SPA（Element Plus）                                  │
└───────────────────────┬────────────────────────────────────┘
                        │ HTTPS / JSON（Bearer Token）
┌───────────────────────▼────────────────────────────────────┐
│  Nginx（生产）                                              │
│  /api/ → gunicorn    / → 静态产物    /media/ → 受控提供      │
└───────────────────────┬────────────────────────────────────┘
┌───────────────────────▼────────────────────────────────────┐
│  Django + DRF                                               │
│  ┌──────────┬──────────┬───────────┬──────────────────┐    │
│  │  core    │ project  │  archive  │     aicore       │    │
│  │ 用户/角色 │ 主业务域  │ 历史档案   │  LLM 接入        │    │
│  └──────────┴──────────┴───────────┴──────────────────┘    │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ flow.py 状态机 · docgen.py 文书 · precheck.py 规则预审 │  │
│  │ prefill.py 字段抽取 · similarity/functions 查重        │  │
│  └──────────────────────────────────────────────────────┘  │
└───────────────────────┬────────────────────────────────────┘
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   SQLite / PostgreSQL          文件系统 media/
```

为什么是单体：使用者是一个市级主管部门的十几个人，数据量在万级。引入微服务只会把「装一套系统」变成「运维一套集群」。四个 Django app 已经提供了足够的模块边界，将来真要拆，按 app 边界拆即可。

## 二、模块职责

### core —— 身份与基础数据

| 组件 | 职责 |
|---|---|
| `models.User` | 继承 `AbstractUser`，增加姓名、角色外键、单位、手机、首次登录改密标记、口令版本号 |
| `models.Role` | 可细分的角色，每个角色映射到一个权限域（`scope`） |
| `models.OrgUnit` | 申报单位名录，九类分组，含别名与启停 |
| `jwt.VersionedJWTAuthentication` | 认证时校验 token 内的口令版本与用户当前版本是否一致，实现 JWT 条件下的吊销 |
| `permissions` | `IsAdminRole` / `IsBusinessUser` 两个权限类 |
| `org_units` | 单位名归一：精确 → 别名 → 去行政区前缀 → 唯一包含 |

**角色与权限域分离**是本模块的关键设计。流程判断只认四个域（申报 / 初审 / 审核 / 管理），而角色表允许把「初审岗（政务）」和「初审岗（产业）」建成两个角色、都映射到 `reviewer`。这样机构调整细分岗位时不用改流程代码。

`is_staff`、`is_superuser` 在 `User.save()` 里按当前角色域强制同步。起因是一个真实漏洞：管理员被改成申报单位后，`is_superuser` 残留，仍可用原密码登录 `/admin/` 直接改库，绕过所有业务口的限制。

### project —— 主业务域

| 组件 | 职责 |
|---|---|
| `models` | Project、ProjectFile、ProjectDocument、ReviewFile、PrecheckReport、SupplementNotice、ProjectEvent、ActionDraft、ProjectCodeSequence、DocTemplate、TodoAck、StageSla |
| `flow` | 状态机：阶段定义、角色映射、可用动作、前置条件、流转执行、留痕 |
| `docgen` | 四份对外文书按模板生成（初审函、任务书、批复、归集证明） |
| `precheck` | 规则预审：几百条勾稽规则，分三级 |
| `prefill` | 从可研正文抽取字段回填申报表单 |
| `parsing` | PDF / DOCX / TXT / XLSX 文本与章节提取 |
| `diff` | 材料版本对比（段落级） |
| `report` | 统计与导出 |
| `archiving` | 归档包导出 |
| `storage` | 文件落盘路径规则 |
| `upload_quota` | 按用户统计上传量与单份上限 |

### archive —— 历史档案与查重

| 组件 | 职责 |
|---|---|
| `models.ArchiveProject / ArchiveFile / CompareReview` | 档案项目、档案文件、比对结论 |
| `services` | 上传入库、解析、按 SHA-256 去重、比对调度 |
| `textparse` | 档案文本与章节提取 |
| `similarity` | 字符 n-gram 向量、余弦相似度、包含度 |
| `functions` | 功能点抽取与匹配（动作词 + 对象词） |
| `extract` | 结构化要素抽取 |

### aicore —— LLM 接入

| 组件 | 职责 |
|---|---|
| `llm` | 配置读写、OpenAI 兼容协议调用、连接测试、密钥掩码、长文分块 |
| `views` | 预设列表、配置读写、连接测试 |

三种部署场景走同一套协议：商用云（填厂商地址与密钥）、单位内网 / 政务云（只改 `base_url` 与 `model`）、完全离线（本机 Ollama，密钥留空）。

## 三、请求链路

以「初审岗提交初审通过」为例：

```
前端点击按钮
   ↓ POST /api/projects/{id}/action/  {action: "precheck_pass", ...}
路由 → ProjectViewSet.action
   ↓
flow.transition(project, user, "precheck_pass", payload)
   ├─ 校验动作是否在 available_actions(project, user) 内  → 否则 403
   ├─ 校验前置条件（规则预审已跑？有 blocking 项？）
   ├─ 事务内：改阶段、写 ProjectEvent、更新关联表
   └─ 返回动作结果
   ↓
序列化返回最新项目状态 + 新的可用动作列表
   ↓
前端按返回的 actions 重新渲染按钮
```

关键点：**可用动作由后端计算并下发**。前端不判断「这个阶段该显示哪个按钮」，只渲染后端给的列表。这样权限与阶段条件的唯一事实源在后端，前端改版不会漏掉一条限制。

## 四、关键技术决策

### 1. 阶段不可直接赋值，只能过状态机

`Project.stage` 字段可以被赋值，但业务代码里没有任何一处直接写它。所有推进都走 `flow.transition`。收益是「状态与留痕永不失配」——每次阶段变化必然伴随一条 `ProjectEvent`，且必然经过前置条件校验。代价是所有新动作都要在 `flow.py` 里登记，不能临时在视图里改状态。

### 2. 权限在三个层面同时生效

| 层面 | 实现 | 拦截什么 |
|---|---|---|
| 接口层 | ViewSet 的 `permission_classes` / `get_queryset` | 越权访问资源 |
| 动作层 | `flow.available_actions(project, user)` | 不该出现的按钮与请求 |
| 数据层 | 查询集按角色过滤 | 看到别家的项目与档案 |

少一层都会漏。只有接口层，前端仍会渲染出点了报 403 的按钮；只有动作层，直接构造请求仍能读数据。

### 3. 文书用模板占位符生成，不用代码拼版式

四份对外文书都是 `.docx` 模板 + `{{placeholder}}` 替换。管理员可在「模板库」上传新版覆盖内置模板，配置文件里的 `org.issuer`、`org.site`、`org.policy_name` 注入占位符。

不用代码拼版式的原因：公文版式（字体、字号、行距、表格、落款右对齐）用 python-docx 从零构造极其冗长，而且改一次版式要改代码。模板方案让「改版式」变成「改 Word 文件」。

替换实现上有一个细节：Word 的一段文字可能被拆成多个 run（尤其经过复制粘贴的模板）。`_replace_all` 先按段落整体匹配，命中后把结果写进第一个 run、清空其余 run，从而保留段落级格式（字体继承自第一个 run，对齐由段落属性决定）。

### 4. 文件按项目分文件夹，不按年月

```
media/projects/XM2026-012_市不动产登记信息平台升级改造/
    01_申报材料/01_申报中/…
    01_申报材料/02_预审中/…
    02_生成文书/立项批复-XM2026-012.docx
    03_评审会材料/专家意见表-1.pdf
```

按年月分会把一个月里十几个项目的材料混在一层。项目本身是天然归档单元。文件夹名在第一次落盘时定型，之后改项目名不搬动——数据库存的是相对路径，搬一次要改一批记录，收益只有「文件夹好看」。

项目名进路径前截断 40 字符：Windows 全路径 260 字符上限，中文项目名三四十字很常见，不截断会出现「文件传了却打不开」。

### 5. 查重分三层，不追求一个综合分

| 层 | 方法 | 输出 |
|---|---|---|
| 功能 | 从可研抽功能点（动作词 + 对象词），按相似度匹配 | 哪条功能对得上，两侧章节 |
| 章节 | 字符 n-gram 向量 + 余弦相似度 | 最像的一章及相似度 |
| 段落 | 段落级 n-gram 包含度 | 左右两栏原文对照 |

不合成单一综合分的原因：初审要判断的是「这两份可研是不是在重复建设」，而这个问题靠一个数字回答不了。给「重合率 62%」不如给「第 3 章都写的是不动产登记一网通办，两边原文这三段基本一致」。

### 6. SQLite 优先，PostgreSQL 可切

默认 SQLite，理由是部署成本：一个文件拷走就是完整数据库，适合「装在办公室一台机器上」的场景。`settings.py` 留了环境变量切换入口：

```bash
export PM_DB_ENGINE=django.db.backends.postgresql
export PM_DB_NAME=pm PM_DB_USER=... PM_DB_PASSWORD=...
```

并发写入压力上来（>20 人同时办件）时应切 PostgreSQL。SQLite 的写锁是库级的，写入高峰会出现等待。

### 7. SPA 由后端同源托管

前端构建产物输出到 `backend/spa/`，Django 用 catch-all 路由返回 `index.html`，`/assets/` 单独处理。收益是部署只有一个进程、没有跨域问题、`/media/` 的鉴权可以直接复用会话。

`index.html` 与静态资源都设了 `no-cache`：开发期反复重建，浏览器拿着旧 HTML 去要已被清掉的旧哈希资源，会出现白屏或旧样式。

## 五、可扩展点

| 需求 | 改哪里 |
|---|---|
| 新增审批环节 | `flow.STAGE_ROLE` 加一行、`Project.Stage` 加枚举、迁移、在 `available_actions` 里加动作 |
| 新增对外文书 | 放模板到 `apps/project/docs/templates/`、`docgen.py` 加一个生成函数、`DocTemplate.Kind` 加枚举 |
| 换本地机构名录 | 改 `org_data.py` 后跑 `load_org_units`，或在 admin 里维护 |
| 新增预审规则 | `precheck.py` 的规则表追加 |
| 接入别的模型 | 系统设置 → 模型接入，不用改代码 |
| 细化角色 | 在 admin 建角色并指定权限域，流程代码不用动 |

## 六、已知限制

1. **限流只在本进程内生效**。Django 默认 LocMemCache，多 worker 部署时登录限流不全局，需把 `CACHES` 换成 Redis。
2. **大文件解析是同步的**。单份 200 MB 的 PDF 解析会占用请求线程数十秒。量大时应改为异步任务队列。
3. **比对是全量内存计算**。档案上千份后，重复建设比对耗时会明显上升，需要预建索引或离线预计算。
4. **无多租户隔离**。一个部署服务一个主管部门，跨部门使用需另行设计数据隔离。
5. **归档包导出只认已验收**。这是业务约束而非技术限制，但代码里做了双保险（视图层 403 + 服务层异常），改动时需同时改两处。
