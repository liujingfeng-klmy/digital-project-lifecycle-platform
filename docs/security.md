# 安全设计

系统的安全边界在哪、做了哪些防护、哪些是已知风险，本文逐项说明。

---

## 一、认证

### JWT 双 token

| 项 | 值 | 理由 |
|---|---|---|
| Access 有效期 | 2 小时 | 从 12 小时缩短。token 万一外泄，可用窗口从半天缩到两小时 |
| Refresh 有效期 | 7 天 | 覆盖一周工作节奏，不打断填表 |
| 刷新轮换 | 开启 | 每次 refresh 签发新 token 并把旧的加入黑名单 |
| 黑名单 | `token_blacklist` app | 登出时把 refresh 作废 |

Access 到期由前端拦截器自动续期，用户无感。

### 两条吊销路径

JWT 是无状态的，签出去就收不回。系统用两条机制补这个缺口：

1. **口令版本号**（`User.token_version`）。token 内带 `tv` 声明，认证时与用户当前值比对，不相等即视为已吊销。改密时 +1 → 所有旧 token 立刻失效。
2. **Refresh 黑名单**。登出时把 refresh 加入黑名单，不能再换新 access。

两条路径覆盖两个场景：改密（版本号）与主动登出（黑名单）。缺一条都会留下「改了密码但旧 token 还能用」或「登出了但 refresh 还有效」的窗口。

### 改密后的连带处理

改密 → `token_version` +1 → 该用户所有设备上的 token 失效 → 强制重新登录。这是有意为之：改密的常见原因就是怀疑泄露。

### 限流

| 接口 | 限额 |
|---|---|
| `/api/auth/login` | 10 次/分钟 |
| `/api/auth/change-password` | 5 次/分钟 |

按 IP 计数。**限制**：Django 默认 LocMemCache 只在单进程内生效，多 worker 部署时限额变成 N 倍。要全局生效需把 `CACHES` 换成 Redis。

## 二、授权

### 三层防护

| 层 | 拦什么 | 实现 |
|---|---|---|
| 接口层 | 越权访问资源 | 每个 ViewSet 的 `permission_classes` 与 `get_queryset` |
| 动作层 | 不该出现的按钮与请求 | `flow.available_actions(project, user)` |
| 数据层 | 看到别人的数据 | 查询集按角色过滤 |

只有一层会漏：接口层能挡请求但前端仍渲染出点了报 403 的按钮；动作层能挡按钮但直接构造请求仍能读数据。三层同时生效才闭环。

### 角色与权限域

流程判断只认四个域：`applicant` / `reviewer` / `auditor` / `admin`。角色表可细分，但细分角色必须映射到一个域。

`is_staff` 与 `is_superuser` 在 `User.save()` 里按当前角色域强制同步。这是一个已修复的漏洞：

> 管理员被改成申报单位后，`is_superuser` 残留为 `True`，仍可用原密码登录 `/admin/` 直接改数据库，绕过所有业务口的限制。

修复方式是把「角色 → is_superuser」的同步放在 `save()` 里，任何改角色的入口都绕不过去。

### 数据隔离的具体口径

| 角色 | 能看到什么 |
|---|---|
| 申报单位 | 只有自己账号创建的项目 |
| 初审岗 / 审核岗 | 全部项目（办件需要） |
| 管理员 | 全部项目 + 历史档案 |
| 初审岗看档案 | 可导入，导入后看不到别家档案的列表、检索、原文、统计 |

最后一条容易做错：初审岗有导入权限，但导入不等于可以浏览全部档案。申报单位在重复建设卡片上只看到结论，不下发别家项目名与原文片段。

## 三、上传安全

### 类型白名单

| 场景 | 允许扩展名 |
|---|---|
| 正文类材料 | `.pdf` `.docx` `.txt` `.xlsx` |
| 评审会材料（扫描件为主） | `.pdf` `.jpg` `.jpeg` `.png` `.webp` `.tif` `.tiff` |

按扩展名判断，不做 MIME 嗅探。理由：用户上传的都是办公文档，MIME 由客户端给、不可信；扩展名是本系统后续解析的分派依据，必须直接控。

**代价**：改扩展名的文件会进入解析流程并失败，但不会被执行（系统只读不执行、不渲染 HTML）。

### 体积限制

| 限额 | 值 | 环境变量 |
|---|---|---|
| 单份文件 | 200 MB | —（`parsing.MAX_BYTES`） |
| 单次请求合计 | 200 MB | `PM_UPLOAD_MAX_BATCH_MB` |
| 单次文件数 | 10 | `PM_UPLOAD_MAX_FILES` |
| 单用户累计 | 5 GB | `PM_UPLOAD_MAX_TOTAL_GB` |

累计配额按「库里 `uploaded_by=该用户` 的原件大小相加」统计，含历史版本与评审会材料——因为它们实际占盘。

Django 层还设了内存阈值：`FILE_UPLOAD_MAX_MEMORY_SIZE = 2.5MB`，超过就走临时文件。这不是「上传上限」，是「内存阈值」——避免 200 MB 的 PDF 整块读进进程内存。

### 去重

同一项目内按 SHA-256 判重，重复上传直接拒绝。避免同一份可研传五遍占五份空间。

### 路径安全

项目名进文件路径前经过 `storage.clean()`：

- 替换 `\ / : * ? " < > |` 与换行、制表符为 `_`
- 去掉首尾空格与点
- 截断到 40 字符

不做这一步会有两个问题：Windows 上非法字符导致文件打不开；全路径超 260 字符（中文项目名三四十字很常见）导致「文件传了却打不开」。

截断长度是按 Windows 上限倒推的，不是随意取值。

## 四、密钥管理

### 签名密钥

不硬编码。取值顺序：

1. `PM_SECRET_KEY` 环境变量
2. `data/.secret_key` 文件（首次启动自动生成 `secrets.token_urlsafe(48)`，权限 600）
3. 都没有 → 生成并落盘

不硬编码的理由：源码一旦外流，硬编码 key 等于任何人都能伪造 token、解密 session。

`.secret_key` 不进版本库，服务器各自独立。备份时必须带上——丢了它，恢复后所有已签发 token 失效。

### 模型密钥

| 环节 | 做法 |
|---|---|
| 存储 | `config.json`，权限 600。建议放项目目录外（`/etc/pm/config.json`） |
| 注入 | 优先读 `PM_LLM_API_KEY` 环境变量，覆盖文件里的明文 |
| 下发 | 接口只返回掩码（如 `sk-****abcd`），不下发明文 |
| 检测 | 若配置内含明文密钥且位于项目目录内，启动时打 WARNING 日志 |

推荐做法：`config.json` 里 `api_key` 留空，密钥只走环境变量。这样连配置文件被拷走都不泄露。

### 敏感配置外置

`config.json` 在 `.gitignore` 里。项目内只保留 `config.example.json`（空密钥、`enabled: false`）。

## 五、DEBUG 模式的边界

`PM_DEBUG=1` 时有两处放开：

1. 详细报错页（含堆栈与配置片段）
2. `/media/` 由 Django 无鉴权托管

这两项在桌面模式是有意的（本机、单用户、绑定 127.0.0.1）。但一旦改绑 `0.0.0.0`，所有原件可被直接下载，且无需登录。

因此：

- `启动.command` 里显式注释了这一点
- settings 默认 `DEBUG=False`，只有显式设置才是 True
- 生产部署的 systemd unit 里不设该变量

生产环境下 `/media/` 必须由后端通过鉴权视图提供，不能让 Nginx 直接指向文件目录：

```nginx
# 错误做法：任何人猜到路径就能下载
# location /media/ { alias /opt/pm/media/; }

# 正确做法：走后端
location /media/ { proxy_pass http://127.0.0.1:8000; }
```

## 七、已知风险

按优先级排列。

| 风险 | 影响 | 缓解 |
|---|---|---|
| 限流不跨进程 | 多 worker 下限流形同虚设 | 生产接 Redis 作 cache backend |
| 无审计日志表 | 谁在什么时候看了哪份原件，事后查不到 | 目前靠 `data/logs/pm.log` 的应用日志 + `ProjectEvent` 的业务留痕 |
| 文件类型按扩展名判断 | 精心构造的恶意文件可能进入解析流程 | 解析器只读取文本，不执行、不渲染 |
| 无 CSRF 令牌 | 纯 token 认证下不适用；若改为 cookie 存 token 则必须补 | 当前 token 存 localStorage |
| localStorage 存 token | XSS 可直接窃取 | 无第三方脚本、无 `v-html` 渲染用户内容；若引入富文本需重新评估 |
| 大文件解析同步阻塞 | 单请求占用 worker 数十秒，并发上传会拖慢全站 | gunicorn 超时设 300；量大时改异步队列 |
| 无多租户 | 一个部署服务一个部门 | 跨部门使用需设计数据隔离 |
| 数据库明文存储 | 拿到文件即可读全部业务数据 | 依赖服务器与备份介质的物理安全；敏感场景需磁盘加密 |

## 八、安全检查清单

部署上线前逐项确认。

- [ ] `PM_DEBUG` 未设置（或为 `0`）
- [ ] `PM_SECRET_KEY` 已设置，或 `data/.secret_key` 存在且权限 600
- [ ] `config.json` 在项目目录外，权限 600，`api_key` 为空或走环境变量
- [ ] `PM_ALLOWED_HOSTS` 已配为实际域名
- [ ] 已启用 HTTPS，HTTP 301 跳转
- [ ] Nginx `client_max_body_size` 已改为 210M
- [ ] `/media/` 走反向代理到后端，未直接 alias 到文件目录
- [ ] 默认演示账号已删除或改密（`admin` / `shenbao` / `chushen` / `shenhe`）
- [ ] `org` 段已配（`issuer` / `site` / `prefixes` / `policy_name`）
- [ ] 备份脚本已就位，且试过至少一次恢复
- [ ] `data/logs/` 有写入权限，日志轮转生效
